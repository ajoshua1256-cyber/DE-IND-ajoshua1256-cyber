- client_contacts: id PK, client FK, full_name, role_title, email, phone, is_primary, timestamps

These fields follow the supplied project documentation. Verification against models.py is still required.

## Relationships

One client can have several contact people. For example, a company may have an accounts officer and a project manager. Each contact record belongs to one client through its client foreign key.

One user can create several clients. Each client records its creator through created_by. The documented deletion behaviour preserves the client and clears this link if the creator is deleted. Contact records are deleted if their parent client is physically deleted. Deactivation instead marks the client as inactive.

## State change walkthrough

An Admin or Project Manager enters client details and any contact information into the Add Client form.

The browser sends JSON to POST /api/v1/clients/ with a login token. The API checks authentication, role permissions, required fields, field formats, and email uniqueness.

The documented creation process generates a reference number within a transaction, saves the client, creates any supplied contacts, and writes an audit entry. The creator is recorded through created_by.

After successful saving, the API returns HTTP 201 with the client details and reference_no. Invalid input should return HTTP 400 without creating a client. Transaction boundaries and rollback behaviour need testing to confirm that a failure cannot leave partial records.

## Privacy

Sensitive item: Client and contact emails and phone numbers. Names, addresses, and notes may also contain personal information.

Who may view/edit: Admin and Project Manager users may view and edit clients. Staff and Auditors may view but cannot edit through this feature. Client users access their own information through separately scoped endpoints. These permissions need verification against the implementation.

What must not enter AI tools: Real client names, emails, phone numbers, addresses, confidential notes, database exports, passwords, secret keys, or login tokens. Use synthetic examples instead.

## Two data failures

1. Duplicate email: An existing email is submitted again. The API should reject it with a clear field error and create no additional client. Differently capitalised emails need testing because validation and lowercasing may behave inconsistently.

2. Reference-number collision: Two users register clients at nearly the same time. The documented transaction and locking mechanism are intended to prevent duplicate references. Concurrent testing must confirm this, including when the database initially contains no clients.

## Test ideas (6+)

1. Create a client with valid synthetic details; expect HTTP 201 and a unique reference number.
2. Submit a missing or empty name; expect HTTP 400 and no new client.
3. Submit an existing email; expect HTTP 400 and no additional client.
4. Submit an existing email with different capitalisation; expect a controlled duplicate error rather than HTTP 500.
5. Create a client with multiple contacts; confirm that every contact links to the correct client.
6. Submit simultaneous registrations; confirm that all successful clients receive different reference numbers.
7. Deactivate a client; confirm that is_active becomes false and the record remains stored.
8. Delete a creator account in an isolated test database; confirm the documented SET NULL behaviour.
9. Simulate contact creation failing; check that the transaction rolls back related changes without leaving partial records.
10. Submit a name of exactly 200 characters, then 201 characters; expect acceptance at the documented limit and rejection above it.
